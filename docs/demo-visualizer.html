Decision trace

System design, explained

Open each design decision for the mechanism and its limit.

The agents propose actions; the runtime and purchase service enforce authority. These four decisions are the core of the demo and the points to explain in an interview.

01 · How one request avoids a second chargeIdempotency across retries, races, and lost responses

The agent runtime creates one stable request_id for its run. A direct API client must supply its own stable ID when retrying. The purchase service stores a unique (tenant_id, request_id) and a fingerprint of the tenant, user, and quote ID.

1 · QuoteServer stores amount, currency, version, owner, and expiry.
2 · Lock and look upTransaction checks the request key before a new purchase.
3 · RecheckOwner, quote, seller, risk limit, and remaining budget are read again.
4 · Commit onceBudget, purchase, ledger entry, audit, and outbox commit together.
Same ID + same quoteReturn the original receipt with idempotent_replay=true; no new ledger row.
Same ID + changed quoteDeny with IDEMPOTENCY_CONFLICT.
Different IDs competing for budgetOnly a purchase that passes the conditional budget update can commit.
If the response disappears after commit:

The runtime retries with the same request ID. If it still cannot confirm the result, it reports PURCHASE_RESULT_UNKNOWN with that ID for reconciliation. The event worker separately uses unique event IDs, so replay cannot create a second final event.

02 · How the agent harness is builtRepeatable replay, bounded Ollama actions, and separate evaluation

One runtime executes two roles. ReplayModel gives deterministic fixture actions for tests and the short demo. OllamaModel supplies real model proposals through a state-specific JSON action schema. The runtime still validates every proposed action and limits model steps, handoff hops, context size, and elapsed time.

Control harness · fast

19 isolated scenarios exercise normal use, forged context, cross-tenant access, quote changes, budget races, lost replies, and event replay. Six fault cases can be repeated without invoking a model.

Live harness · variable

12 untrusted seller-text prompts drive actual Ollama actions. Model trials run separately with per-case and total wall-clock limits, START/END progress, and a JSON checkpoint after each case.

Independent outcome check

The grader reads purchase, ledger, budget, and event tables instead of accepting an agent's success claim. Runtime-generated answers must match a separately authored fixture oracle.

Honest answer origin

The UI labels fixture replay, real model action, and runtime-sourced final answers separately. New model-written prose needs review; a sourced fallback is a system result, not proof that the model wrote the answer.

Try python3 scripts/run_security_benchmark.py --suite controls --profile smoke --backend postgres for a fast control run. The live suite is a separate command and may take minutes.

03 · Which security controls guard the boundaryIdentity, least privilege, untrusted data, canonical state, auditability
Verified identity

Short-lived, signed local tokens are checked for signature, issuer, audience, and time. The service checks the user's current tenant, active state, and scopes in the database on sensitive calls.

Authority intersection

Current user scopes, task grants, role allowlists, and resource policy all have to agree. The researcher has only the catalog read tool. A handoff never transfers buyer purchase authority.

Handoff and return gates

The packet is checked for run, tenant, sender, parent span, expiry, schema, size, and sourced facts. Forged or over-scoped context is denied and traced.

Untrusted content stays data

Seller descriptions and task text carry trust labels. The model may see them, but instructions inside them cannot change user scopes, task grants, prices, or backend policy.

Canonical commerce

The model never supplies the charged amount. The purchase service re-reads its stored quote and seller state, checks ownership and budget, then writes one atomic mock purchase.

Durable evidence

Allow/deny decisions carry trace and span IDs. Purchase, audit, and outbox writes are atomic; a replaying worker deduplicates final events by event ID.

04 · Safety facts you must know before presentingWhat the demo proves, and where the boundary still ends
  • No real money or customer data. The buyer spends fictional cents in a mock ledger. The identity provider, paid report, and security-event sink are local or simulated.
  • Model action ≠ model-authored answer. The paid answer is assembled from the purchased report. A free answer can be a clearly labeled runtime fallback, even when Ollama proposed the preceding actions.
  • The task spend grant is in the agent runtime. The direct demo API accepts an otherwise authorized purchase without a signed, task-specific grant. A deployed agent system would need that grant at the API boundary.
  • The benchmark is scoped. Deterministic controls and a small live attack corpus test named conditions. They do not establish universal prompt-injection resistance, production payment safety, or cloud-scale reliability; independent blind review remains a release gate.
  • This UI stays local. The optional server binds to 127.0.0.1, requires a per-process request token, and runs each click in a temporary SQLite database. Opening the HTML file alone only shows an illustrative sample until you import a real JSON result.
Good interview phrasing

“I can show the exact boundary each test exercises, its stored evidence, and the limitations. I would add server-verifiable task consent and real integration testing before claiming production readiness.”
